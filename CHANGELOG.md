## [Unreleased]

### Changed

- **The Playbook Captain shell becomes a controller host: one session Captain, one durable conversation, and host-validated actions.** The compiled default Captain is now constructed at `init` with its own playbook session id and the host controller port, lives outside the engagement stack for the whole shell session, and receives every Boss turn — the lazily constructed internal root, the hidden deliver-or-dismiss lifecycle classifier, and the ask-first refusal of a second registered command are all retired. Registered commands resolve deterministically before any model call (idle `/cmd text` starts, `/cmd text` at the leaf delivers, an enabled command absent from the active path switches, a bare command or one naming an active non-leaf ancestor answers only), and the resolution reaches the runtime as the linker-exposed controller port's `resolveParsedTurn`, so `handleBossInput` keeps exactly `{ text, signal }`. Everything else settles through one hidden durable decision call whose validated `respond` | `start` | `switch` | `dismiss` | `deliver` | `runtime` selection returns to the shell for validation and execution: registry membership, an idle shell for `start`, an active root and an off-path target for `switch`, an active leaf for `dismiss` / `deliver` / `runtime`, and the leaf's own `describe()` advertising the action id for `runtime` — an invalid selection settles `rejected` with a reason, no effect, and shell-owned status text. Delivered text is shell-authoritative (the exact Boss text, or a same-command turn's parsed remainder), a `start` / `switch` input is provenance-tagged `origin: 'boss' | 'captain'` and never silently defaulted, and a settlement with status `ok` is final for the turn. Captain prose reaches Boss only as validated captain speech through cligent `CaptainContext.emitReply`; `emitStatus` carries none. The acting turn's closing reply is composed by the session Captain from the settlement's outcome report — the facts verbatim, the receipt disposition and its normalized error, the leaf-state summary, and the exact counts — and the `summaryPolicy` saved-counts line is supplied for it only when the turn's counted activity is nonzero, so `Saved you 0 …` can no longer follow a turn that saved nothing ([DR-029](specs/decisions/029-session-scoped-conversational-captain.md), [IR-036](specs/iterations/036-session-scoped-conversational-captain.md), [CAPTAIN-1](specs/user/playbook-captain.md#captain-1), [CAPTAIN-2](specs/user/playbook-captain.md#captain-2), [CAPTAIN-19](specs/user/playbook-captain.md#captain-19), [CAPTAIN-7](specs/dev/playbook-captain.md#captain-7), [CAPTAIN-8](specs/dev/playbook-captain.md#captain-8), [CAPTAIN-9](specs/dev/playbook-captain.md#captain-9), [CAPTAIN-16](specs/dev/playbook-captain.md#captain-16), [CAPTAIN-20](specs/dev/playbook-captain.md#captain-20), [CAPTAIN-13](specs/test/playbook-captain.md#captain-13), [CAPTAIN-21](specs/test/playbook-captain.md#captain-21), [CAPTAIN-37](specs/test/playbook-captain.md#captain-37), [CAPTAIN-38](specs/test/playbook-captain.md#captain-38)).

- **The session Captain's conversation is durable, and a broken one is replaced instead of lost.** Every session-Captain call — the decision call, a parse-resolved command reply, and the acting turn's closing reply — runs hidden on one conversation whose returned `resumeToken` the shell pins in place of the prior pin, while interleaved sub-runtime judge calls stay fresh and never touch that pin. A call that throws, returns non-`ok`, or returns `ok` without a token marks the conversation unsynchronized: the pin is cleared and that one call is re-issued exactly once on a fresh conversation seeded with the shell's own deterministic reseed digest of the session journal plus the current ControlView digest — never a reseed plus another retry — and only the model-side conversation is replaced, so the engagement stack, player sessions, journal, and the turn's already-executed work all survive. The journal itself is host-kept, append-only, JSON-safe, never Boss-visible, and exists only for that reseed; a raw journal record reaches no prompt. A second consecutive continuity failure fails the phase with a Boss-appropriate reply naming a concrete next step, the stack untouched and the raw diagnostic left on trace telemetry ([DR-029](specs/decisions/029-session-scoped-conversational-captain.md), [CAPTAIN-31](specs/dev/playbook-captain.md#captain-31), [CAPTAIN-35](specs/dev/playbook-captain.md#captain-35), [CAPTAIN-34](specs/user/playbook-captain.md#captain-34), [CAPTAIN-39](specs/test/playbook-captain.md#captain-39), [CAPTAIN-40](specs/test/playbook-captain.md#captain-40)).

- **Raise the registry dependency closure to cligent 0.19.** `@sublang/cligent` moves from `^0.18.0` to `^0.19.0`, and the lockfile pins the published `0.19.0` with its registry integrity hash, because the controller shell consumes two surfaces 0.18 does not ship. `CaptainRunResult.resumeToken` is the durable Captain conversation's pin: the shell replaces the prior pin after every session-Captain call, and its absence is exactly what marks a conversation unsynchronized and triggers the single journal-seeded reseed. `CaptainContext.emitReply` is the captain-speech surface: the explicit `captain_reply` channel that renders validated Captain prose as ordinary Captain speech rather than as a bracketed `emitStatus` line, which is the only path controller prose has to Boss now that every decision and closing-reply call runs hidden. The bump was held until 0.19.0 published — a committed manifest whose range no committed resolution satisfies is what [RELEASE-19](specs/test/release.md#release-19) rejects on behalf of [RELEASE-14](specs/dev/release.md#release-14) — so the range and the lockfile move together here, with the git-ignored [RELEASE-11](specs/dev/release.md#release-11) local-development override removed first so the regenerated lockfile records the registry resolution and no `link:` anywhere. This closes the [IR-036](specs/iterations/036-session-scoped-conversational-captain.md) landing unit and turns [RELEASE-28](specs/dev/release.md#release-28)'s nested-cligent floor guard green, so the opt-in live acceptance suite now drives a candidate whose installed cligent carries both surfaces ([RELEASE-4](specs/dev/release.md#release-4), [RELEASE-12](specs/dev/release.md#release-12), [CAPTAIN-9](specs/dev/playbook-captain.md#captain-9), [CAPTAIN-31](specs/dev/playbook-captain.md#captain-31)).

- **The default Captain playbook is recompiled to the session-scoped controller.** The rewritten `reference/sdlc/captain.md` compiles through the SLC pipeline into new `reference/sdlc/captain.playbook/` GEARS, FSM, and linked-runtime artifacts. The machine is a session loop, not a finite errand: a parked conversational hub receives every Boss turn; one decision per turn selects from the closed action set `respond` | `start` | `switch` | `dismiss` | `deliver` | `runtime` (the stable controller guard contract); an acting selection's controller-port settlement grounds one closing-reply call; and the machine returns to the hub — with exactly one `type: 'final'` shutdown state entered only by the host's teardown event, no terminal `{ response }` output, no nested `callPlaybook`, and no Boss-reply suspension (a clarifying question to Boss is a `respond` selection). The linked module becomes a thin artifact over the shared `createXStatePlaybookRuntime` factory with a `spec.compat` declaration: the host-supplied controller port rides the linked options, every decision and closing-reply call runs `{ visibility: 'hidden' }` with the decision reply validated as `{ action, … }` control JSON under exactly one corrective re-ask (a second malformed reply settles the turn back at the hub with no action executed), a parse-resolved turn enters with its injected decision object and no decision call, and Boss turns map deterministically from the host's command-parse resolution with no classifier judge call. The compiler contracts land alongside: `slc/gears2fsm.md` §Setup gains the additive controller decision-state class, `slc/link.md` gains the controller Captain-call presentation and the rewritten §Boss-event mapping entries, the engine gains the additive controller spec seams (`captainStrategy`, hidden-call trace form, an options-aware classifier), and the regenerated `.slc-verify` bundle and suites pin the new source–FSM–artifact agreement including the six CAPPLAY-20 prompt-contract re-pins ([DR-029](specs/decisions/029-session-scoped-conversational-captain.md), [IR-036](specs/iterations/036-session-scoped-conversational-captain.md), [CAPPLAY-6](specs/dev/captain-playbook.md#capplay-6), [CAPPLAY-16](specs/dev/captain-playbook.md#capplay-16), [CAPPLAY-18](specs/dev/captain-playbook.md#capplay-18), [CAPPLAY-11](specs/test/captain-playbook.md#capplay-11), [CAPPLAY-19](specs/test/captain-playbook.md#capplay-19), [CAPPLAY-20](specs/test/captain-playbook.md#capplay-20)).

### Added

- **A broken markdown cross-reference now fails the suite.** `pnpm test` resolves every relative link in `specs/`, `CHANGELOG.md`, and `README.md`: the target file must exist, and any `#` fragment must match an anchor the target actually renders. Anchors are derived exactly as GitHub derives them, which is the part that matters — a character dropped from between two spaces leaves both spaces behind, so `### 11. Host adapter — tmux-play` answers only to `#11-host-adapter--tmux-play` with two hyphens, and any derivation that collapses repeated hyphens accepts the broken single-hyphen spelling silently; a near miss of that shape is reported with the spelling that would have worked. File existence alone is not enough either: the link that prompted this resolved to a file that *did* exist, in the wrong spec group, and only the anchor check caught it. Duplicate slugs take `-1` / `-2` suffixes, explicit HTML `id` / `name` anchors resolve, and reference definitions are checked like inline links, while text inside a fenced code block or an inline code span is not treated as a link at all — so a document may quote link syntax as prose, as DR-018 and `meta.md` both do. A target that resolves outside the project directory is a failure rather than a pass, so a link that only worked because a sibling checkout happened to sit beside this one can no longer ship — two links into `../../../cligent/` did exactly that and are now repointed at cligent's published URL, the form DR-004, DR-009, and DR-027 already use. The check also runs standalone as `pnpm check:links` ([IR-037](specs/iterations/037-markdown-cross-reference-check.md), [XREF-1](specs/dev/cross-references.md#xref-1), [XREF-2](specs/dev/cross-references.md#xref-2), [XREF-3](specs/test/cross-references.md#xref-3), [XREF-4](specs/test/cross-references.md#xref-4)).

- **The engine owns a control surface: every shared-factory runtime now describes itself and applies advertised actions.** Runtimes built by `createXStatePlaybookRuntime` implement the optional `describe`/`apply` pair of `@sublang/playbook/runtime` (declared both-or-neither, feature-detected like the parked-session snapshot capability — no ABI or schema bump). `describe()` is a side-effect-free ControlView over the live snapshot: normalized state, the context projection the runtime itself authors — the FSM context members that artifact names and nothing else, so a member is private until named and a member added to an FSM later stays private — pending Boss questions with ids, the last recorded error, and the currently valid actions — a failure-state retry that replays the recorded last classified event with its recorded payload, and resumable-state jumps sent as the FSM's explicit-state-jump event with textual fields omitted, each labeled from source state descriptions and validated against live guards; a candidate whose payload cannot be sourced from recorded state is excluded rather than completed with invented text. `apply({ actionId, key, signal })` revalidates against the live state (`rejected` before any effect), executes at most once per idempotency key with the receipt recorded at acceptance — a repeated key returns the recorded receipt without re-execution, while a key that never reached acceptance (a thrown call or a `rejected` revalidation) records nothing and may execute later — and settles `executed` with the run result or `failed` with the normalized error after effects may exist. Past acceptance the call does not throw: a settlement failure there is a post-acceptance control-plane error and becomes the `failed` receipt, so a caller is never handed an exception over an effect that already happened. Apply boundaries trace as paired schema-2 `apply.started`/`apply.finished` events carrying action id, key, and receipt disposition ([DR-029](specs/decisions/029-session-scoped-conversational-captain.md), [IR-036](specs/iterations/036-session-scoped-conversational-captain.md), [PBRT-5](specs/dev/playbook-runtime.md#pbrt-5), [PBRT-34](specs/dev/playbook-runtime.md#pbrt-34), [PBRT-52](specs/dev/playbook-runtime.md#pbrt-52), [PBRT-53](specs/test/playbook-runtime.md#pbrt-53)).

- **`pnpm smoke:release` verifies a release candidate without a single model call.** Maintainers of this repository get one command — it ships in the repository, not in the published package — that packs the candidate with `npm pack` and drives eight steps against that tarball inside one isolated temporary root, stopping at the first failure and preserving the root so it can be inspected: the lean global install carries the nested cligent and no SDK directories; the opted-in install carries both agent SDKs as top-level roots; the installed `playbook --help` and `--list` name `code` and `discuss`; a bare-repo hermetic run provisions the engine once and provisions nothing on a second run; the packed compiled artifacts hash-equal the committed ones and their conformance suites rerun green; and the nested installed cligent satisfies the documented floor and really carries `CaptainContext.emitReply` and `CaptainRunResult.resumeToken` — each proven a member of its own interface by type-checking a fixture that uses it at the type the shell uses it at, resolved through the same `@sublang/cligent/tmux-play` specifier the shell imports. Looking for the two names instead cannot fail here: `resumeToken` names members of four unrelated cligent declarations and `emitReply` survives in a neighboring record type's doc comment, so a text scan stays green with both members deleted from the interfaces the shell calls. It spends no credential and creates no tmux session, but it does need npm registry access, because two of its steps install from it. It claims GEARS↔FSM↔runtime fidelity only — the SLC pipeline is agentic, so nothing here re-derives an artifact from its markdown source, and no suite reads the maintained `reference/sdlc/captain.md`. The pre-release ordering is now `pnpm test` → `pnpm smoke:release` → `pnpm test:acceptance` → the conditional manual UX smoke, and the opt-in live acceptance suite grows from four scenarios to five, the fifth exercising the conversational Captain end to end against real agents ([IR-036](specs/iterations/036-session-scoped-conversational-captain.md), [RELEASE-10](specs/dev/release.md#release-10), [RELEASE-24](specs/dev/release.md#release-24), [RELEASE-28](specs/dev/release.md#release-28), [RELEASE-25](specs/test/release.md#release-25), [RELEASE-29](specs/test/release.md#release-29)).

### Removed

- **`composeCaptainPrompt` and `composePlayerPrompt` no longer exist on `@sublang/playbook/captain/playbook`.** The rewritten controller Captain composes its decision prompt through the engine's shared `defaultComposeCaptainPrompt` and its corrective re-ask through its own builder, and it calls no players at all, so the two prompt functions the previous compiled Captain exported have no caller and no meaning under the session-loop machine. Both were named exports of a subpath [RELEASE-20](specs/dev/release.md#release-20) declares public and semver-stable, and there is no drop-in replacement for anyone who imported them directly instead of using the shell that ships with the package, because the prompts they built described a machine that no longer exists. **This is a breaking removal under [RELEASE-1](specs/dev/release.md#release-1). Whether to carry it is still open: if it stands, the release is a major; restoring the two functions as deprecated compatibility exports would keep it a minor.** The earlier reading that it might be a minor — that RELEASE-20 pinned the subpath and no item pinned its members — is withdrawn: at 4.0.0 both functions were module-level named exports of `captain.playbook.js` *and* `export declare function` declarations in `captain.playbook.d.ts`, and importing them through the package's own `@sublang/playbook/captain/playbook` specifier resolved and called them. Intent, internal convention, and silence in the docs do not unship a declared export. RELEASE-20 now states which unit of a compiled-playbook subpath is semver-stable — the entry plus every top-level named and default export of the JavaScript and declarations behind it, with `_internal` members explicitly outside it — and [RELEASE-21](specs/test/release.md#release-21) pins those export sets for `./captain/playbook`, `./code/registry`, and `./discuss/registry`, so the next such removal goes red at the gate and is decided before the tag rather than after ([DR-029 Addendum A2](specs/decisions/029-session-scoped-conversational-captain.md#addendum-a2-the-rewrite-removes-two-named-exports)). Nothing else leaves: the subpath's type re-exports persist and gain `CaptainControllerPort`, `CaptainControllerInput`, `CaptainControllerSelection`, and `CaptainParsedResolution`; `@sublang/playbook/code/playbook` is untouched; and the shared adjudication builder `defaultBuildCaptainJudgePrompt` stays exported from `@sublang/playbook/xstate-runtime` ([DR-029](specs/decisions/029-session-scoped-conversational-captain.md), [RELEASE-15](specs/dev/release.md#release-15), [CAPPLAY-11](specs/test/captain-playbook.md#capplay-11)).

### Fixed

- **A host port that rejects no longer costs the Boss their settlement.** Effect attribution was recorded at the operation that threw, which was right, but the boundary around that operation enclosed a whole region of the turn: the leaf check, the visibility request, the mode change and its telemetry, the runtime call, and the processing of its result all sat inside one wrapper. A `setVisiblePlayers` rejection on a delivered turn, or a telemetry sink rejecting the shell transition made one line before the runtime call, was therefore filed as an *effect* failure and propagated with the runtime never invoked — the turn ending with nothing surfaced and nothing statused, exactly the outcome attribution was tightened to prevent. Each boundary now encloses one call expression naming one of the four operations the contract enumerates, and the drive and apply paths agree that processing what a runtime returned is not itself an effect. Two standing guards close the class from both ends: one reads what is passed to each boundary rather than only where it sits, and one makes every host port the shell is handed reject in turn and fails unless the turn still reaches one Boss-visible settlement ([CAPTAIN-35](specs/dev/playbook-captain.md#captain-35), [CAPTAIN-39](specs/test/playbook-captain.md#captain-39)).
- **An identifier the host supplied is guarded wherever the host supplied it.** The rejection duty covering machine-shaped identifiers the shell puts into a turn's prompts was enforced by two calls in one digest composer, so the blocks nobody named sat outside it: a reseed recap replaying an earlier action put that action's id back into the prompt with nothing live advertising it, and the degraded digest a runtime without a control surface takes read the wrong field name entirely — the contract calls it `questionId` and both shipping runtimes emit it under that name, so a mirrored question reached the prompt with no id at all. The duty also carried an undocumented three-character floor that excused exactly the short ids a runtime is most likely to mint (`q1`, `5`); the floor was compensating for a raw substring match, so the match is token-aware now and the floor is gone. Registration follows the prompt rather than the composing site: the shell walks the records it renders, so a field either record grows later is guarded without the composer being edited, while the grounding the same digest publishes — the state description, its tags, the context projection — stays outside the duty, a reply being meant to reflect it ([CAPTAIN-9](specs/dev/playbook-captain.md#captain-9), [CAPTAIN-40](specs/test/playbook-captain.md#captain-40)).
- **No field a runtime or a registry publishes can forge a block in the Captain prompt.** The shell frames foreign content in labeled blocks, and escaping was applied field by field: the context lines and the pending questions went through the bounding-and-escaping seam while the advertised action's id and label and the enabled playbook's intent — three plain strings in the same function — were interpolated raw. A newline in any of them opened a second `[Boss message]` or `[Catalog digest]` inside the composed prompt, the forged instruction reading to the model as host-authored and the forged catalog sitting above the real one. Every foreign value now becomes part of a digest line through one seam, so a line added later carries the property without restating it ([CAPTAIN-9](specs/dev/playbook-captain.md#captain-9), [CAPTAIN-40](specs/test/playbook-captain.md#captain-40)).
- **`PlaybookRuntimeOptions.controller` is declared required, as the implementation has required it since the shell rework.** It was optional at the type level only until that rework landed, and the docstring said so; the rework landed, the shell supplies the port on every construction, and the public declaration was the only thing still admitting its absence — so `createPlaybookRuntime({ enabledPlaybooks })` typechecked into a runtime that fails its first Boss turn. Construction from untyped JavaScript still reaches that named fail-fast error rather than a silent one ([CAPPLAY-9](specs/dev/captain-playbook.md#capplay-9)).
- **A refusal the session Captain is told about is told once.** The shell carries a refused selection forward to the pinned conversation as one labeled block on the next turn-opening call. "Once" was counted per port invocation while the prompt is composed once per model *call*, so a turn whose reply needed a corrective re-ask delivered the block on both calls — the second time beside the rejection notice — and a turn that aborted after the notice was cleared delivered it on neither, leaving the next turn with no record of the refusal at all. The block is claimed by the first composition that carries it and the notice cleared only when a call that carried it comes back; a reseeded re-issue needs no second copy, its recap carrying the same refusal from the journal ([CAPTAIN-35](specs/dev/playbook-captain.md#captain-35), [CAPTAIN-39](specs/test/playbook-captain.md#captain-39)).
- **A refused selection is no longer forgotten by the session Captain.** The Boss saw `Cannot do that: …`, but nothing else did: the refusal reached no journal record and no prompt, so the durable conversation remembered proposing an action and never learned it had been refused — a follow-up "why?" or "do it anyway" then answered a turn the model believed had succeeded. The root cause is the one the previous round fixed for the failure reply and left open on this branch: the journal writer sat on the *model-prose* seam rather than on the *Boss-visible* one, so two of the three settlements recorded themselves and the third did not. Every Boss-visible settlement now leaves through one seam that emits, journals, and marks the turn together, with a refusal recorded under its own `refusal` kind rather than dressed as captain speech. The journal only feeds a reseeded conversation, so the pinned one gets its own remedy: the refusal rides the next call that opens a Boss turn as a shell-composed labeled block naming what was proposed, which side refused, and why — host-authored, inside the prompt exclusions, and costing no extra model call ([CAPTAIN-34](specs/user/playbook-captain.md#captain-34), [CAPTAIN-35](specs/dev/playbook-captain.md#captain-35), [CAPTAIN-9](specs/dev/playbook-captain.md#captain-9), [CAPTAIN-39](specs/test/playbook-captain.md#captain-39)).
- **A failed status emission is no longer blamed on an effect that provably never ran.** `apply()` could return a `rejected` receipt — the runtime's own statement that it refused before any effect — and if the Boss pane then rejected the refusal line, the shell classified that presentation failure as an *effect* error and propagated it, ending the turn with nothing surfaced at all even though the reply channel worked fine. The flag was set before `apply()` and read at the turn-wide catch, so everything downstream of the first attempt inherited the attribution regardless of what actually threw. Attribution now follows the operation that threw: it is recorded at the effect invocation itself and read back by the identity of the value that escaped it, so there is no latch to inherit, and a failure to *present* a settlement settles the turn with the failure reply through the channel that remains. A rejected receipt also decides the turn's finality the moment it arrives, so a turn whose refusal could not be shown no longer claims that work ran ([CAPTAIN-35](specs/dev/playbook-captain.md#captain-35), [CAPTAIN-39](specs/test/playbook-captain.md#captain-39)).
- **An advertised action id can no longer reach the Boss through the reply that names it.** The digest hands the model complete action ids on purpose — the decision reply selects by one — and a `jump:<stateId>` id embeds a state the machine is by construction *not* in, so the reply validator's live-state check could never reach it and action ids were exempt outright. That exemption proved the ids were not confidential; it never proved they were Boss-appropriate, which is the property the privacy rules regulate, and the shipped suite pinned the leak (`Resumed from planAndImplement; …` surfaced unchanged). Three changes close it at once. The runtime never labels an action with an identifier: a jump whose target publishes no description is not advertised at all, and a retry falls back to its own source state's description rather than to the target id or the replayed event type — a label that *is* an id made the host's id-to-label substitution a no-op. The host now rejects, in any Boss-visible text, the machine-shaped identifiers it itself put into this turn's prompts — the advertised action ids, their `<verb>:`-stripped fragments, and the pending questions' ids — read from its own record of what it composed, never from a list of literals, and still never refusing a bare English word. And the refusal status line, previously the one Boss-visible settlement passing through no validation at all while quoting the most foreign text of the three, now passes the same check and degrades to a fact-free refusal rather than printing a reason it cannot vouch for ([CAPPLAY-5](specs/user/captain-playbook.md#capplay-5), [CAPTAIN-34](specs/user/playbook-captain.md#captain-34), [CAPTAIN-9](specs/dev/playbook-captain.md#captain-9), [PBRT-52](specs/dev/playbook-runtime.md#pbrt-52), [CAPTAIN-38](specs/test/playbook-captain.md#captain-38), [CAPTAIN-40](specs/test/playbook-captain.md#captain-40), [PBRT-53](specs/test/playbook-runtime.md#pbrt-53)).
- **A parallel machine no longer publishes one region's meaning as the whole state's.** `stateDescription` is a single string and the host that receives it cannot inspect it for completeness, so returning the first matching region's description stated a fraction as the whole and the host relayed it verbatim. While more than one region is active the runtime now publishes a description per region, deterministically ordered and carrying no region *name* (which is itself a state id), and publishes none at all when any active region has none — "a description per active region" is satisfiable or it is not. Each region's description is resolved by that region's qualified state path rather than by its leaf state key, because a leaf name such as `idle` or `failed` is exactly the one a machine reuses in every region — a leaf-keyed index resolved two regions to one description and published it as the meaning of both, which is the same false statement arrived at from the other end. The covering form is reachable through the shared factory, contrary to an earlier note in this entry: the factory admits one active `meta.playbook` state id per snapshot and a description is not a state id, so one region publishing through `meta.playbook` and another through a plain source `description` reaches it. It now carries live rows instead of a claim of unreachability ([PBRT-52](specs/dev/playbook-runtime.md#pbrt-52), [CAPTAIN-9](specs/dev/playbook-captain.md#captain-9), [PBRT-53](specs/test/playbook-runtime.md#pbrt-53)).
- **The public-API release gate now sees type-only exports.** The gate added to stop a second accidental breaking removal compared one recorded set of names against both the JavaScript module and its declaration file, which forced its declaration scan to match only the forms the JavaScript also carries — `export declare function|const|class|let|var` — and so left roughly forty exported interfaces, type aliases, and `export type { … }` re-exports unpinned, `CaptainControllerPort` among them, which is the type of `PlaybookRuntimeOptions.controller` that every host must implement to construct the runtime. The two sets are now recorded separately, the declaration scan covers every export form, and the scan itself is proven falsifiable by removing one export of each form. Which subpaths are pinned is derived from `package.json`'s `exports` map minus one recorded exclusion rather than listed, so a subpath added to the manifest goes red until it is recorded — a list left `./xstate-runtime`, `./code/playbook`, `./playbook-captain`, and `./discuss/playbook` unpinned, and adding one name would have left the next. A wildcard re-export naming a relative in-package target is resolved and enumerated into that subpath's recorded set, in the `export *` form and the `export type *` form alike; one naming anything else fails, that being the case no enumeration can resolve. The type form is the one that matters in a declaration file, and a rejection written for the value form neither rejected nor enumerated it ([RELEASE-20](specs/dev/release.md#release-20), [RELEASE-21](specs/test/release.md#release-21)).
- **Dropping a running playbook no longer repeats its last state line.** Dismissing an engagement, or switching away from one, showed the dropped playbook's current state twice — `◆ failed` immediately before `◇ /checklist stopped`, `⤷ outline` twice on a plain dismissal — because `dispose()` stopped the XState actor with inspection still live. Stopping a still-running actor makes XState emit one final snapshot carrying the *unchanged* state value with `status: 'stopped'`, and the runtime read it as a state entry: it re-ran the state's status composition and appended a phantom self-loop `fsm.transition` trace and `playbook.fsm.state` telemetry beside the visible duplicate, redundant with the `session.disposed` trace emitted immediately after. Disposal now suppresses inspection before stopping, as the failed-start and snapshot-restore paths already did, so a disposed runtime reports exactly one boundary — its own `session.disposed` — and any state it was parked in is announced once, when it was entered. A runtime that reached a final state was never affected: its actor had already run its stop procedure, so the stop was a no-op. The reference DISCUSS runtime keeps its own actor rather than the shared factory's, so it needed the same fix and did not inherit it; both it and the engine now stop through a single seam that suppresses first, and the suite discovers every runtime source that builds an actor and fails unless each has exactly one such site, so the next such artifact is covered by construction ([IR-036](specs/iterations/036-session-scoped-conversational-captain.md), [PBRT-6](specs/dev/playbook-runtime.md#pbrt-6), [PBRT-22](specs/test/playbook-runtime.md#pbrt-22)).
- **A dismissed engagement can no longer leave the shell reporting itself as engaged.** The shell selects `chat` before it unwinds the stack, and it disposes a frame before it pops it — so telemetry a runtime emitted on the way down still found itself the active leaf, and a parked state descriptor in that telemetry moved the authoritative mode straight back to `engaged.parked`, leaving an emptied stack reported as engaged in the control ledger with a leaf whose actor was stopped. The shell now mirrors only telemetry that is evidence about a live leaf: a payload whose actor status is not `active` is a teardown artifact, and a payload from a frame whose disposal has already begun belongs to an engagement that is going away. Both pass through to the host untouched and update neither the leaf ledger nor the mode. The guard is the shell's own and does not rest on any runtime's disposal hygiene, so it holds for a runtime the shell did not author ([CAPTAIN-10](specs/dev/playbook-captain.md#captain-10), [PBRT-22](specs/test/playbook-runtime.md#pbrt-22)).
- **A leaf's private FSM state no longer reaches the Captain conversation.** The ControlView exported every JSON-safe member of a runtime's FSM context, which for CODE meant the resolved host player roster, the per-run option values, and raw player output — reviews, rebuttals, whole prior results — all pasted into the durable session-Captain prompt as one JSON document, in a digest required to exclude rosters and option values and to admit player output only as fenced quotes. The view's context is now an explicit projection each runtime authors, and the shell renders it one bounded, escaped line per exported member instead of inlining it, so no exported value can forge a second labeled block into the prompt envelope or crowd the rest of the digest out of it. CODE exports its four workflow-classification members; the session Captain exports its settlement evidence. A `describe()` that exists and then throws is also no longer reported as a leaf that *advertises no control surface* — a false claim about a leaf that may advertise many actions: the digest names the read failure and reports the advertised actions as unknown rather than none, and, as with genuine capability absence, only the machine verbs are bounded while `respond` stays valid ([DR-029 Addendum A1](specs/decisions/029-session-scoped-conversational-captain.md), [PBRT-34](specs/dev/playbook-runtime.md#pbrt-34), [PBRT-52](specs/dev/playbook-runtime.md#pbrt-52), [CAPTAIN-9](specs/dev/playbook-captain.md#captain-9), [PBRT-53](specs/test/playbook-runtime.md#pbrt-53), [CAPTAIN-37](specs/test/playbook-captain.md#captain-37), [CAPTAIN-40](specs/test/playbook-captain.md#captain-40)).
- **A host call can no longer start after its turn was aborted.** Every traced call boundary — player, direct-Captain, and judge — now re-checks its combined signal between the awaited `*.call.started` emission and the host port invocation, so an abort that lands while that emission drains (for example, fired from the telemetry sink observing it) settles the already-started pair as `aborted` with no host call made; previously the boundary's pre-call checks could not see that window and the host call started anyway. The same window in the new `apply()` boundary settles before acceptance — no action execution, no receipt recorded, the idempotency key left free — with its `apply.finished` trace carrying the canonical rejected-before-any-effect receipt disposition required of every apply finish, and a finish sink rejecting that abort finish surfaces from the boundary in place of the abort, matching the settlement-drain precedence of the other public boundaries; a failure-state retry action is now labeled from the recorded `BOSS_INTERRUPT` event's own `targetId` rather than the first configured arm of a guarded transition list ([PBRT-13](specs/dev/playbook-runtime.md#pbrt-13), [PBRT-52](specs/dev/playbook-runtime.md#pbrt-52), [PBRT-18](specs/test/playbook-runtime.md#pbrt-18), [PBRT-51](specs/test/playbook-runtime.md#pbrt-51), [PBRT-53](specs/test/playbook-runtime.md#pbrt-53)).
- **The Captain now speaks about a run's state in words instead of state ids.** The ControlView carries `stateDescription` — the runtime's own Boss-facing statement of what its current state means, written from the same source state descriptions its action labels come from — and the shell's digest hands the model that description in place of the `state value <id>` line it used to. This closes a contract that could not be satisfied: a status answer had to be grounded in the digest, and the digest's only state grounding was an identifier the Boss surface forbids, so the landed acceptance rows asserted the violation. Nothing invents a description: a state whose source declares none publishes none, and a leaf with no control surface at all publishes none either — the digest then says so rather than falling back to the id it holds from telemetry. Only with no prompt carrying an id does the host take on a rejection duty for one, and a narrow one: a reply carrying a live *machine-shaped* state id — read from the live stack, never from a list of literals — is refused with one corrective re-ask, while a live id that is an ordinary English word (`ready`, `failed`) is left alone, because refusing the word "failed" would refuse plain speech ([DR-029 Addendum A3](specs/decisions/029-session-scoped-conversational-captain.md), [PBRT-52](specs/dev/playbook-runtime.md#pbrt-52), [PBRT-34](specs/dev/playbook-runtime.md#pbrt-34), [CAPTAIN-9](specs/dev/playbook-captain.md#captain-9), [CAPPLAY-5](specs/user/captain-playbook.md#capplay-5), [PBRT-53](specs/test/playbook-runtime.md#pbrt-53), [CAPTAIN-37](specs/test/playbook-captain.md#captain-37), [CAPTAIN-40](specs/test/playbook-captain.md#captain-40)).
- **A failed turn's reply is no longer forgotten by the next Captain.** Every Boss-visible Captain reply now leaves the shell through one seam that journals it, the host's own "I could not finish that turn" fallback included — it previously went straight to the Boss pane with no record, so a conversation replaced after a continuity failure saw the Boss's next message with no idea what the host had last said, and could read "okay, do that" as agreement to work that never ran. The same fallback is now Boss-facing in what it names: an executed or refused runtime action is named by the label its runtime advertised, never by the action id, and the composed reply passes the same prose validation every model reply passes — where the recorded facts quote runtime-authored text that fails it, the reply drops the facts and still states that the work ran and what to ask next, rather than printing unvalidated text ([CAPTAIN-34](specs/user/playbook-captain.md#captain-34), [CAPTAIN-9](specs/dev/playbook-captain.md#captain-9), [CAPTAIN-35](specs/dev/playbook-captain.md#captain-35), [CAPTAIN-39](specs/test/playbook-captain.md#captain-39)).
- **A runtime that refuses an action, or cannot be asked, no longer ends the turn in silence.** When the active runtime returned a `rejected` receipt, the shell folded it into settlement facts and returned to its hub: no closing reply, no captain speech, and no refusal status line either, because the shell only surfaced refusals it raised itself — and the silent-turn guard was suppressed by the fact that a selection had been submitted. Both refusals now reach the same status line, naming the action by its advertised label and the reason it was refused. Separately, a `describe()` that throws while the shell revalidates a selection is no longer misfiled as an effect failure: nothing had been attempted, so the selection is refused with a reason naming the read failure instead of the exception escaping the Boss turn with nothing surfaced. An effect error is now marked where the effect is attempted rather than inferred from where a throw was caught ([CAPTAIN-34](specs/user/playbook-captain.md#captain-34), [CAPTAIN-9](specs/dev/playbook-captain.md#captain-9), [CAPTAIN-38](specs/test/playbook-captain.md#captain-38)).
- **`apply()` no longer reports two different final dispositions for one action.** A rejecting `apply.finished` telemetry sink rewrote the already-emitted `executed` receipt to `failed` and destroyed the run result with it, so the caller was told that work which had succeeded had failed — irrecoverably, since accepted receipts are final for their key, and pointlessly, since the `executed` disposition was already on the wire and no rewrite could make the trace and the return agree. Publication is now an explicit line: a settlement failure before the finish emission still folds into the receipt (nothing has been published, so trace, return, and replay can still be made to agree), while one at or after it leaves the receipt alone and travels on the runtime's emission-failure channel to surface from the next public boundary that drains. A receipt states what happened to the effect; a telemetry sink going offline is not that ([PBRT-52](specs/dev/playbook-runtime.md#pbrt-52), [PBRT-53](specs/test/playbook-runtime.md#pbrt-53)).
- **The linker contract can regenerate the artifacts it is supposed to generate.** `slc/link.md` still described the ControlView context as a sanitized serialization of the FSM context — the allow-by-default behavior the projection replaced — carried no rule for authoring or emitting the projection at all, and closed §Output's emitted-spec list without it, so a linker following the document would have produced an artifact that either leaked the whole FSM context or exposed none of it, undoing the privacy fix on the next re-link. §Control surface now states the authored-projection contract and names `controlContextFields`; §Output lists it, states that its default is nothing rather than everything, and requires the `_internal` composers each machine actually uses instead of a fixed player-and-Captain pair the controller Captain cannot satisfy. The suite now checks those clauses are still stated where a linker would read them, and discovers every linked artifact in the repository to fail unless each declares its projection ([PBRT-52](specs/dev/playbook-runtime.md#pbrt-52), [PBRT-35](specs/test/playbook-runtime.md#pbrt-35), [PBRT-53](specs/test/playbook-runtime.md#pbrt-53)).
- **A transient empty agent reply no longer costs the whole turn.** cligent keeps `PlayerRunResult.finalText` optional, so any adapter may legally return `status: 'ok'` with no text; the engine previously failed the turn at once (`captainBridge: callPlayer returned status=ok with no finalText`), and its two call boundaries disagreed on whether `''` counted as empty. The delegated-player bridge and the direct-Captain boundary now treat a missing, empty, or whitespace-only `finalText` under one shared predicate and re-issue the same call exactly once — the corrective call traced as its own started/finished pair, a corrective player call continuing the player session under the stored resume selection — before a second such result follows the existing failure path unchanged. The linked DISCUSS reference runtime applies the same predicate and re-ask at its player boundary. Non-`ok` results, thrown calls, aborts, and rejecting finish-trace sinks are never retried ([DR-028](specs/decisions/028-empty-ok-result-re-ask.md), [IR-035](specs/iterations/035-empty-ok-result-re-ask.md), [PBRT-9](specs/dev/playbook-runtime.md#pbrt-9), [PBRT-47](specs/dev/playbook-runtime.md#pbrt-47), [PBRT-23](specs/test/playbook-runtime.md#pbrt-23), [PBRT-51](specs/test/playbook-runtime.md#pbrt-51)).

Running via `npx` follows the same principle with different mechanics — no install command reaches npx's ephemeral tree, so the documented form names each SDK as a sibling package of one invocation: `npx -y -p @sublang/playbook -p <sdk> playbook`. *Correction:* an earlier draft of this entry shipped peer ranges mirroring cligent's own (`>=0.3.154`, `>=0.138.0`); the mirror froze the first time cligent's floor moved, and the runtime-compatibility delegation below removes the declaration entirely ([DR-026](specs/decisions/026-optional-adapter-sdks.md), [IR-033](specs/iterations/033-optional-adapter-sdks.md), [RELEASE-12](specs/dev/release.md#release-12), [RELEASE-13](specs/test/release.md#release-13), [RELEASE-27](specs/test/release.md#release-27), [sublang-ai/slc#6](https://github.com/sublang-ai/slc/issues/6)).

Only the runtimes actually at fault are named (an `opencode` whose CLI is present and in range names the SDK alone), every printed remedy installs cligent's pinned repair spec (`npm install -g <package>@<verified-version>`), and the npx re-run names pinned specs too, so a repair can never install a version the gate would refuse again. `gemini`'s exemption ends: its CLI can be absent or below floor, and the descriptor names both, so it is gated like every other adapter. ### Added

- **A missing agent SDK now fails at the gate with the command that fixes it.** Both `playbook` and `playbook run` probe each declared adapter through cligent's own `adapter.isAvailable()` — the same dynamic import the adapter performs at run time, from the same installed module scope, so a passing probe cannot disagree with a failing run. An unavailable SDK blocks before tmux-play is spawned or any agent call is made, names every affected adapter, and prints each one's exact remedy: `npm install -g <sdk>` for an installed tree, plus the global install of any external CLI the adapter's probe also requires (`opencode` names both `@opencode-ai/sdk` and `opencode-ai`), or — when the run is detected inside npm's ephemeral `npx`/`npm exec` tree, which no install command can reach — one multi-package re-run that is executable exactly as printed: it names the running package at its own version, the SDK of **every** mapped adapter the lineup requires as sibling `-p` packages (not only the missing ones — each distinct package set materializes a distinct exec tree, so a missing-only re-run drops the SDKs the current tree does have and two partial trees alternate forever), and ends with the original invocation's arguments, shell-quoted, in place of a placeholder no launch surface accepts — including a task or reply the command consumed from stdin, since that pipe is gone when the printed command runs. Stdin-derived values ride behind a new `--` end-of-options terminator in the `run` argument grammar, because quoting alone cannot keep a flag-shaped value from being reinterpreted on the replay: a bare `--json` task would flip on the JSON envelope, and a `--last` reply would silently resume the most recent session with the session id demoted to the reply text. An invocation that already activated its own terminator keeps it and gets no second one — parsing stops at the first `--`, so a doubled marker would itself become positional data and turn the replayed task into `-- --json`; a `--` consumed as an option's value (`--cwd --`) does not count as active. A missing adapter's external CLI install is printed before the re-run, so following the output top-to-bottom succeeds without a second hop. A resumed run is gated on its stored lineup the same way. The gate initially covered the adapters backed by optional peer SDKs (`claude`, `codex`, `opencode`); the runtime-compatibility delegation above extends it to every adapter cligent publishes targets for, `gemini` included. The check is independent of the credential check, so a config missing both reports both rather than sending the user round the loop twice ([PBCLI-39](specs/dev/playbook-cli.md#pbcli-39), [PBCLI-40](specs/user/playbook-cli.md#pbcli-40), [PBCLI-41](specs/test/playbook-cli.md#pbcli-41)).

- **The engine exposes its direct-Captain adjudication prompt builder.** `@sublang/playbook/xstate-runtime` now exports `defaultBuildCaptainJudgePrompt`, the single statement of the hidden judge's `{ guard, …structuralPayloadFields }` reply contract over a state's declared result keys. Compiled Captain artifacts compose their adjudication prompts through it instead of restating the contract, so the wording cannot drift out of agreement with the adjudicator that parses the reply ([DR-025](specs/decisions/025-resilient-captain-control-adjudication.md), [CAPPLAY-18](specs/dev/captain-playbook.md#capplay-18), [RELEASE-15](specs/dev/release.md#release-15)).

### Fixed

CODE is the first registered playbook. ## [0.4.0] - 2026-05-28

### Changed

- **Breaking:** `captain.options.coderPlayer` / `reviewerPlayer` are no longer required in the host configuration. The tmux-play adapter now derives the per-run player identity strings (substituted into `<coder-llm>` / `<reviewer-llm>` placeholders in player prompts) from `players[].adapter` at init time per PBRT-4, removing the duplication with the `players:` section. Stale `captain.options.coderPlayer` / `reviewerPlayer` keys in existing user configs are silently ignored; delete them at your convenience. The bundled template, dev config, production config, and `playbook-code --help` text no longer mention these keys.
- Captain-pane status stream redesigned per PBRT-3: glyph vocabulary shrinks to three (`⤷` state entry as `<Player>: <label>`, `→` guard outcome as `→ <guard>[ · field=N]`, `◆` failure/awaitBossReply only). The `◆ ready` and `◆ done` tombstones are no longer emitted — the next `boss>` prompt is the implicit turn-over signal. The Boss-input echo is replaced with a bare classification line carrying only the FSM event type (e.g., `START_CODING`), which the host renders as captain speech. State entries no longer carry the source-item tag (`CODE-N`) or the rider fields (`intent=…`, `irNumber=…`, `taskDescription=…`); the Boss readline already shows the verbatim Boss text. The runtime emits each line as bare content with no leading whitespace; speaker chrome (the current cligent `captain> [status] …` prefix) and any visual nesting under parent lines are presentation concerns and remain the host's responsibility.

### Fixed

- Player-prompt composer now arranges labelled blocks around the body based on the body's directional language: `Boss intent:` and `Task description:` stay above the body as prior context, while `Review items:` and `Rebuttals:` are appended below the body so the CODE-N prompts' "for each review item below" / "for each rebuttal below" phrasing matches the rendered layout. Previously every labelled block was prepended, contradicting the body's instructions. The continuation preamble + Q/A blocks still precede every ordinary block. PLAYBOOK-5 and DR-004 §6 updated.

## [0.2.0] - 2026-05-24

### Added

- Boss-reply suspension. Any captain-invoking state can now pause when the player surfaces a clarifying question for Boss: the FSM parks at `awaitBossReply` and the Captain pane shows the question; Boss's next turn is normally classified as the reply (a clearly fresh directive abandons the pending question instead), and the same state resumes with the Q+A in its prompt. DR-005 introduced the path, IR-006 implemented it, and IR-008 made it universal across every captain-invoking state.

### Changed

- **Boss turns are now plain language; the judge is the sole classifier.** Every non-empty Boss turn is passed to the judge, which classifies it into one of the FSM's events (or `NO_ACTION`); the judge picks `BOSS_INTERRUPT` targets from the FSM's jumpable states by their human-readable descriptions. There is no slash fast-path — text starting with `/` is treated as ordinary Boss content. (IR-009)
- Bundled `tmux-play` configs (dev and production) now set `permissions.mode: auto` on the captain and both roles, so each agent runs in cligent's protected auto mode (claude `permissionMode: 'auto'`, codex `on-request + auto_review`). Routine in-session approval prompts are suppressed.

### Removed

- The four slash commands `/start <intent>`, `/continue <#>`, `/summarize <#>`, and `/interrupt <stateId>` are no longer recognized by the runtime. Their behavior is now reached by typing the same intent in plain language (see Changed). The `/command` namespace is reserved for host-level playbook selection. (IR-009)
- Framework-injected "If a specific Boss answer is needed, ask the exact question and stop." player-prompt instruction. Boss-reply suspension still works: a clarifying question that naturally appears in player prose is detected by the adjudicator's `needsBossReply` classification — no nudge prompt is needed. (IR-010)
